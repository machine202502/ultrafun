# Архитектура

Как устроен код и куда класть новое. Разделы с правилами обязательны: код следует им. Раздел «Карта модулей» описывает текущее состояние и обновляется вместе с кодом. Принцип: **простые структуры данных, явная передача, логика игры отделена от всего остального.**

## Главное правило

**Крейт `game` — чистая логика игры.** Он не знает про окно, GPU, звук и ввод с клавиатуры: в его `Cargo.toml` нет `winit`, `wgpu`, `kira`, `egui`, поэтому нарушить правило невозможно — код просто не скомпилируется. Он получает действия игрока и шаг времени, обновляет состояние и сообщает, что произошло.

Остальные модули читают состояние игры и реагируют на события, но не меняют правила.

Зачем: логику можно тестировать без окна, запуская тысячи шагов в тесте. Агент, который правит рендер, не сломает геймплей, и наоборот.

```
          ввод ОС
             │
          input/  ──── Actions ────┐
                                   ▼
                               game/  (чистая логика)
                                   │
                ┌─── состояние ────┼──── Vec<GameEvent> ───┐
                ▼                  ▼                       ▼
            render/              ui/                 audio/, fx/
```

## Карта модулей

> Карта описывает, **что есть сейчас**. Она следует за кодом: добавил, переименовал или перенёс модуль — обнови карту в той же задаче. Все остальные разделы этого документа — **правила**, им следует код.

Cargo workspace из двух крейтов. Новые крейты — только по правилам раздела «Скорость компиляции».

### Крейт `game` — логика (зависит только от glam, parry3d, serde, rand)

| Файл | Отвечает за |
|---|---|
| `lib.rs` | `Game`: всё состояние мира, порядок шага `update()`, события `GameEvent`, `Actions`, `GameConfig`, стрельба |
| `player.rs` | Данные игрока, состояния движения `MoveState`, взгляд |
| `movement.rs` | Приёмы движения: бег, прыжок, рывок, скольжение, стены, слэм |
| `motion.rs` | Перемещение любого тела-капсулы: скольжение вдоль стен, ступеньки, пол |
| `collision.rs` | Мир столкновений и запросы к parry3d (протаскивание, касания, лучи) |
| `config.rs` | Конфиги движения и здоровья (из RON) |
| `level.rs` | Описание уровня: боксы, старт, мишени, враги, арены, выход |
| `weapon.rs` | Конфиг оружия, мишени, трассировка выстрела |
| `enemy.rs` | Болванка: ИИ, атака, расталкивание |
| `parts.rs` | Детали-лечилки |
| `arena.rs` | Арены: триггер, волны, станок, двери; `impl Game` для их шага |

Тесты логики — `game/tests/*.rs`, общие помощники — `game/tests/common/`.

### Крейт `ultrafun` — приложение (зависит от `game`)

| Файл | Отвечает за |
|---|---|
| `main.rs` | Запуск, логирование, цикл событий |
| `app/mod.rs` | `App`: владеет всем; окно, ввод с клавиатуры и мыши, захват курсора |
| `app/frame.rs` | Один кадр: шаги логики с фиксированным шагом, раздача событий, камера, отрисовка |
| `app/reload.rs` | Перезагрузка файлов данных и уровней на лету, переключение уровней |
| `app/screenshot.rs` | Режим скриншотов: расстановка камеры по кадрам и сохранение снимков |
| `input.rs` | Клавиши и мышь → `Actions` по раскладке из настроек |
| `settings.rs` | Настройки из `settings_default.ron`, параметры рендера |
| `assets.rs` | `DataFiles`: чтение RON и слежение за изменениями папки |
| `levels.rs` | Какой уровень грузить: тестовая комната (RON) или уровень из Blender |
| `level_loader/` | Уровень из Blender: `scene.rs` — чтение glTF, `mod.rs` — сборка уровня по именам объектов, `tests.rs` — тесты и тест маршрута |
| `render/` | wgpu: `mod.rs` — `Renderer` и кадр; `scene_pass.rs` — конвейер и привязки сцены; `lights.rs` — лампы и выбор ближайших; `shadows.rs` — кубические карты теней; `lightmap.rs` — запекание отражённого света в лайтмап на CPU; `style.rs` — стиль освещения и режимы; `upscale.rs` — низкое разрешение и растягивание; `level_mesh.rs` — вершины боксов; `*.wgsl` — шейдеры |
| `fx.rs` | Косметика по событиям: следы, отметки, вспышки, свечение, цвета врагов и мишеней |
| `audio.rs` | Звуки по событиям (kira) |
| `dispatcher.rs` | Реплики Диспетчера по событиям |
| `text.rs` | Тексты для игрока из `assets/text/<язык>.ron` |
| `ui.rs` | HUD: прицел, здоровье, субтитры, отчёт; сборка `Hud` из состояния игры |
| `overlay.rs` | egui: отрисовка HUD, отладочной панели F1 и лаборатории света F3 поверх кадра |
| `lighting_lab.rs` | Панель F3: выбор режима освещения, ползунки, сохранение режима |
| `screenshots.rs` | Список кадров из `tools/screenshots.ron` и порядок съёмки «все режимы × все кадры» |

`examples/placeholder_sounds.rs` — генератор звуков-заглушек.

### Ресурсы и инструменты

```
assets/
├── data/          — RON: движение, оружие, здоровье, враг, настройки, режимы освещения, тестовая комната
├── levels/        — уровни из Blender: <имя>.glb + <имя>.ron
├── audio/         — звуки
└── text/          — тексты для игрока по языкам
art/levels/        — исходники уровней (.blend)
tools/blender/     — скрипты генерации уровней и моделей
tools/screenshots.ron — кадры для режима скриншотов (`cargo run --release -- --screenshots`)
docs/              — документы для человека
```

Подробно об ассетах — [assets.md](assets.md).

### Поток данных за кадр

```
клавиши, мышь ─► input.rs ─► Actions ─► game::Game::update (×N шагов по 1/120 с)
                                              │
                         состояние мира ◄─────┤────► Vec<GameEvent>
                               │                          │
          render/ (боксы, свет), ui.rs (HUD)     fx.rs, audio.rs, dispatcher.rs
```

Папки и файлы создаются, когда появляется первый код для них. Заранее пустые модули не заводить.

## Главный цикл

- Логика обновляется с **фиксированным шагом 120 Гц**: накопитель времени, `game.update(&actions)` столько раз, сколько накопилось; длительность шага — константа `game::STEP_SECONDS`. Не больше 8 шагов за кадр, иначе отбросить остаток.
- Отрисовка идёт с частотой кадров и интерполирует позиции между двумя последними шагами логики.
- `game` никогда не читает системное время. Время в логике — только `STEP_SECONDS`, умноженный на число шагов.

## Состояние

- Одна структура `Game` владеет всем состоянием мира. `App` владеет `Game`, рендером, звуком и остальным.
- Сущности — обычные структуры в `Vec`: `Vec<Enemy>`, `Vec<Projectile>`. ECS не используем.
- Разновидности — через `enum` и `match`: `EnemyKind::Grunt`. Trait-объекты только если `match` стал реально неудобен.
- Ссылаться на сущность между кадрами — через числовой `id`, не через индекс и не через ссылку.
- Нет глобальных переменных, синглтонов, `Rc<RefCell<…>>`, `Arc<Mutex<…>>`. Всё передаётся явно через `&` и `&mut`.
- Программа однопоточная. Потоки создают только библиотеки (например, звуковой поток `kira`).

## Связь между модулями

- `game.update()` складывает произошедшее в `Vec<GameEvent>`: `EnemyKilled { position }`, `WeaponFired { kind }`, `PlayerDamaged { amount }`.
- После шагов логики `App` раздаёт события в `audio/`, `fx/`, `ui/`, затем очищает список.
- Это обычный вектор `enum`, а не шина событий с подписками.

## Ввод

- `input/` превращает клавиши и мышь в **действия**: `Jump`, `Dash`, `Fire`, `AltFire`, `Look(dx, dy)`.
- `game/` видит только действия и никогда не видит конкретных клавиш.
- Так раскладка клавиш, переназначение и геймпад добавляются в одном месте и не трогают логику.

## Данные

- Числа баланса — в `assets/data/*.ron`, загружаются в структуры через `serde`.
- В отладочной сборке файлы данных перезагружаются на лету при изменении (`notify`).
- Случайность в `game/` — только через генератор с seed, который хранит `Game`. Тест с тем же seed даёт тот же результат.

## Тексты и языки

Игра выходит сначала на английском, русский добавляется позже. Чтобы перевод не требовал переделки кода:
- **Весь текст для игрока** (интерфейс, ранги, реплики Диспетчера, таблички) — в `assets/text/en.ron`, а не в коде. Код обращается к тексту по ключу: `"rank.overtime"`, `"dispatcher.reject_announced"`.
- Русский — это просто `assets/text/ru.ron` с теми же ключами. Нет ключа в переводе — показывается английский.
- Логи и отладочный вывод — на английском прямо в коде, это не текст для игрока.
- Шрифт игры должен поддерживать кириллицу с первого дня.

## Соглашения

- Система координат: правая, **Y вверх**, единицы — **метры, секунды, радианы**. Совпадает с glTF.
- Ошибки загрузки и инициализации — `anyhow::Result`. Нарушение инвариантов в логике — `panic!`/`expect`. Внутри `update` нет `Result` без реальной причины.
- Профилирование — только под cargo-фичей `profile` (см. [stack.md](stack.md)).

## Скорость компиляции

Rust компилирует **крейт целиком** как единицу. Изменение в крейте пересобирает его и всех, кто от него зависит; соседние крейты не трогаются. Библиотеки (wgpu, egui и т.д.) собираются один раз и дальше не пересобираются. Поэтому архитектура строится так, чтобы обычная правка трогала как можно меньше кода.

### Правила

1. **Контент — это данные, а не код.** Уровни (`.glb`), баланс, волны врагов, параметры оружия и врагов, тексты — в `assets/`. Новый уровень или правка числа **не требуют компиляции вообще**, в отладочной сборке подхватываются на лету. Никаких больших таблиц и `match` с цифрами в Rust-коде.
2. **Логика отдельно от тяжёлого.** Крейт `game` не зависит от wgpu, egui, kira. Его тесты (`cargo test -p game`) собираются за секунды и не трогают рендер. Это основной цикл работы агента над геймплеем.
3. **Зависимости идут в одну сторону.** `ultrafun` → `game`, никогда наоборот. Правка в приложении (рендер, UI, звук) не пересобирает `game`.
4. **Новый крейт — по стабильной границе, а не по размеру.** Выделять, когда часть кода (а) заметно замедляет пересборку и (б) имеет узкий, редко меняющийся интерфейс. Кандидаты в будущем: `render`, `level_loader`. Мелкие крейты «на всякий случай» не заводить.
5. **Без тяжёлых обобщений на границах крейтов.** Обобщённые (generic) функции компилируются заново в каждом крейте, который их использует. В публичном API `game` — конкретные типы.
6. **Без своих процедурных макросов и больших `macro_rules!`.** Разрешены готовые derive (`serde`, `bytemuck`).
7. **Минимум возможностей (features) у зависимостей.** Включать только нужные: меньше кода собирать.

### Бюджет

| Сценарий | Цель |
|---|---|
| Правка в `game` → `cargo test -p game` | до 5 с |
| Правка в приложении → `cargo build` | до 10 с |
| Правка данных в `assets/` | без компиляции |

Бюджет превышен — сообщи человеку и найди причину через `cargo build --timings`, прежде чем выделять новый крейт.

### Настройки сборки (уже сделаны)

- Windows: линковщик `rust-lld` (`.cargo/config.toml`) — пересборка примерно вдвое быстрее. На Linux Rust использует lld по умолчанию.
- Зависимости в отладке собираются с оптимизацией (`opt-level = 3`), наш код — с `opt-level = 1`: игра не тормозит, а пересборка остаётся быстрой.
- Во время работы — `cargo check` для поиска ошибок, `cargo build` только для запуска.

## Как расти

- Новое игровое понятие — новый файл в `game/src/`; станет больше ~300 строк — папка с несколькими файлами (как `level_loader/`, `render/`).
- Новый модуль — строка в «Карте модулей».
- Файл больше ~300 строк — разделить по смыслу.
- Модулю понадобилось то, что лежит в другом, — передай параметром, не делай глобальным.
- Хочется добавить новый слой, менеджер или систему — сначала проверь по [principles.md](principles.md), нельзя ли без него.
