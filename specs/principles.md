# Принципы

Проект пишут LLM-агенты. Значит, код оптимизируется под одно: чтобы следующий агент быстро понял его и безопасно поменял.

## 1. Минимальное работающее решение

Делай самое простое, что решает задачу сегодня.

- Нет абстракций «на вырост». Интерфейс с одной реализацией, фабрика для одного класса, базовый класс для одного наследника — не нужны.
- Нет конфигурации, флагов и параметров, которые никто не просил.
- Нет обобщения, пока нет трёх реальных повторов. Два похожих куска кода — нормально.
- Нет паттернов ради паттернов. Если без паттерна получается короче и понятнее — без паттерна.
- Понадобится сложнее — усложним тогда. Это дешевле, чем поддерживать ненужную сложность.

**Проверка:** можно ли удалить слой, параметр или файл, и всё продолжит работать? Если да — удали.

## 2. Меньше кода

- Каждая строка — это то, что агент должен прочитать, понять и не сломать.
- Используй стандартную библиотеку и уже подключённые зависимости, прежде чем писать своё.
- Удаляй мёртвый код сразу. Не комментируй его, не оставляй «на всякий случай» — есть история файлов.
- Не дублируй логику, которая уже есть в проекте. Сначала поищи.

## 3. Без комментариев

В коде нет комментариев. Совсем.

- Смысл передают имена функций, переменных и типов.
- Непонятный кусок — переименуй или вынеси в функцию с говорящим именем, а не поясняй.
- «Почему так» записывается в `specs/decisions.md` или в спек фичи, а не в код.
- Исключения: директивы, которые требуются инструментам (`# type: ignore`, `// @ts-expect-error`, лицензионный заголовок, если обязателен). Ничего другого.

**Почему:** комментарии устаревают молча. Агент верит комментарию, а код делает другое. Имя функции устаревает громко — его видно в каждом вызове.

## 4. Практичность

- Цель — работающая игра, а не образцовая кодовая база.
- Не переделывай рабочий код, если задача этого не требует.
- Не «улучшай» попутно то, что не просили. Заметил проблему — сообщи, а не чини молча.
- Хорошо сейчас лучше идеально никогда.

## 5. Критичность

- Если задача ведёт к лишней сложности — скажи и предложи проще.
- Если спек противоречит здравому смыслу или коду — укажи на это до начала работы.
- Если не уверен — проверь (запусти, прочитай код), а не угадывай.
- Не соглашайся с человеком из вежливости. Аргументированное «нет, вот почему» полезнее.

## 6. Код для LLM

Агенты видят код кусками, ищут по тексту и не держат в голове весь проект. Поэтому:

- Явное лучше неявного. Никакой магии: рефлексии, динамических имён, скрытых побочных эффектов.
- Всё ищется grep'ом. Уникальные, полные имена; не собирай имена из строк.
- Локальность. Всё, что нужно для понимания функции, видно рядом с ней.
- Плоская структура. Мало уровней вложенности папок и наследования.
