# Журнал решений

Неочевидные решения, которые агент иначе мог бы переиграть. Одна запись — несколько строк. Новые записи сверху.

Формат:

```
## YYYY-MM-DD — Короткое название
**Решение:** что выбрали.
**Почему:** главная причина.
**Отвергли:** что рассматривали и почему нет (если важно).
```

## 2026-11-12 — Quality-first model and combat slice
**Решение:** ради качества и темпа можно ломать legacy API/форматы и не поддерживать обратную совместимость. Первый production pipeline строится вокруг проверяемого боевого фрагмента: GLB rigid-модели с UV, отдельный viewmodel pass, три инструмента × два режима, swept projectiles/beam, навигационные waypoint и новая лаборатория на 24 пространства.
**Почему:** старый box-only renderer, один hitscan и XZ-only chase препятствовали читаемым моделям, разнообразному оружию и вертикальному бою. Пользователь выбрал результат и ощущение вместо миграции старой архитектуры.
**Отвергли:** переписывание универсального движка, ECS и новые зависимости; они не нужны для текущего slice. Старые карты не являются acceptance-критерием нового уровня.

## 2026-10-30 — Уровень «Охлаждение»: пилот новой модели + процедурная музыка
**Решение:** третий уровень (горизонт −3, 23 пространства в трёх актах) собран скриптом `tools/blender/cooling_blockout.py` по новой модели построения (типология комнат, ритм, геометрия без общих стен, материалы атласа, свет по комнатам, декор слоями — модель зафиксирована в `design/levels.md`). `validate_geometry: true` — уровень собирается только с чистой геометрией (246 боксов, 0 конфликтов). Взгляд игрока на старте задаётся `spawn_yaw_degrees` в RON уровня (поворот пустышки `player_start` теряется при экспорте glTF). Музыка: процедурные петли `music_calm.wav`/`music_battle.wav` (генератор `examples/placeholder_music.rs`, детерминированный), спокойная играет на уровне, боевая — на арене, переключение по событиям `ArenaStarted`/`ArenaCleared`.
**Почему:** владелец просил большой живой уровень «не из чистых кубов» с текстурами и музыкой; модель уровней выводится по пилоту и применяется к следующим.
**Отвергли:** ручную сборку в Blender — невоспроизводимо агентами; случайный подбор музыки — детерминизм проекта.

## 2026-10-29 — Атласы персонажей: генератор + манифест разметки
**Решение:** `assets/textures/characters.png` (512×512, 64px тайлы) с текстурами игрока (#4417: визор-цель, маркировка «4417» трафаретом), Болванки, Сварщика, Инспектора и Погрузчика; разметка `<персонаж>.<часть>` — в `characters.ron`. Генератор — `examples/generate_characters.rs`, детерминированный, само-тестируемый. Атласы — заготовка для генератора 3D-моделей, в игру пока не подключены.
**Почему:** владелец просил атласы персонажей сейчас, модели — позже внешним генератором; манифест даёт генератору машиночитаемую раскладку.

## 2026-10-29 — Меню уровней плитками и шрифты Russo One + PT Mono
**Решение:** выбор уровня — сетка плиток со снимком уровня (`assets/levels/previews/<имя>.png`), подписью и рамкой выбранного; клик или Enter загружает. Превью снимаются самой игрой (`cargo run -- --make-previews`: кадр сцены со стартовой точки, без HUD и меню). Шрифты: Russo One (пропорциональный, заголовки) + PT Mono (моно, терминальный текст) — оба OFL с кириллицей, в `assets/fonts/`, запись в CREDITS. В ULTRAKILL используется VCR OSD Mono — бесплатен, но без кириллицы, поэтому пара выше; философию «машинного терминала» держит PT Mono.
**Почему:** владелец просил меню как в ULTRAKILL: плитки уровней со скринами, капслок-типографика; кириллица обязательна с первого дня.
**Отвергли:** VCR OSD Mono как основной — латиница-only; генерацию превью при сборке — слишком медленно для CI, команда запускается вручную при добавлении уровня.

## 2026-10-29 — Декор уровня: меши `deco_` без коллизий, кит из Blender-скрипта
**Решение:** любой меш с именем `deco_*` в glb уровня — рендер-только: треугольники с плоскими нормалями и цветом материала, без коллизий, без участия в лайтмапе и тенях стен. Набор моделей (камень, колонна, статуя болванки, ящик, бочка, труба, поддон, щебень, сосулька) генерируется `tools/blender/decor_kit.py` (Blender из Steam, 5.2.3, фиксированный seed 1681) в `assets/models/decor_kit.glb` + `.blend` в `art/decor/`. Уровни инстансируют модели с префиксом имени.
**Почему:** владелец просил живые уровни «не из чистых кубов»; декор без коллизий нельзя сломать и он не мешает движению; скрипт делает модели воспроизводимыми и лицензии我们的 (CC BY-SA).
**Отвергли:** декор с коллизиями — ломает движение и валидацию; uv-разворот и текстуры на декоре — потом, если плоских цветов мало; генерацию glb на Rust — Blender уже есть и это зафиксированный пайплайн уровней.

## 2026-10-29 — Текстуры уровня: один генерируемый атлас, белый тайл-заглушка
**Решение:** все текстуры уровня живут в одном атласе 512×512 с тайлами 64×64 (`assets/textures/atlas.png` + манифест `atlas.ron`). Атлас генерируется детерминированно кодом (`cargo run --example generate_atlases`), без внешних источников — лицензия наша, стиль единый, грязь по краям запечена в тайлы как в ULTRAKILL. Материал назначается кубу в RON уровня по имени объекта; текстура умножается на цвет куба (тинт). Нетекстурированные кубы сэмплируют выделенный белый тайл — одна ветка кода, старые уровни выглядят как раньше. UV — мировые координаты грани, приведённые к метражу тайла; повтор через `fract` в шейдере, nearest-фильтрация без мипов (PS1-стиль, швов нет благодаря полутексельному отступу). Файла атласа нет — рендер уходит на белый тайл 1×1 с предупреждением.
**Почему:** владелец просил разнообразие «не майнкрафтовскими квадратами»; готовые паки CC0 разнородны по стилю и требуют проверки лицензий каждого файла, а генератор даёт единый язык и мгновенные правки. Один атлас = один биндинг в шейдере, без массивов текстур.
**Отвергли:** массив атласов по темам — на старте не нужно, 64 слотов хватает; мип-уровни и линейную фильтрацию — против PS1-чёткости; внешние CC0-текстуры — стиль.

## 2026-10-29 — Remote debug: TCP 127.0.0.1:4852 за флагом, RON-протокол
**Решение:** игра с флагом `--remote-debug` слушает `127.0.0.1:4852` (одно соединение, неблокирующий опрос раз в кадр). Протокол — построчный RON (`serde` уже есть, ноль новых зависимостей). Команды: `State`, `Screenshot`, `LookDelta`, `Pointer` (виртуальный указатель в HUD), `Press`/`Release`/`MoveInput`, `Reload`, `SetLevel`. Ввод агента складывается с вводом игрока, при конфликте игрок главный. Клиент для агента — `examples/remote_probe.rs`. Назначение: отладка живой сессии человека без перезапусков.
**Почему:** владелец устал от цикла «перезапусти — поправь — опять перезапусти»; агенту нужно видеть то, что видит человек (позиция + луч камеры + скриншот), чтобы чинить по описанию «вот здесь сломана текстура».
**Отвергли:** готовые протоколы (gRPC и т.п.) — новые зависимости ради десяти команд; файловый обмен — медленно и не даёт управления вводом. Намеренно нет команд выхода из игры и записи произвольных файлов; сервер только на localhost и только с флага.

## 2026-10-29 — Z-fighting: валидатор геометрии вместо правки на глаз
**Решение:** мерцание стен ловится валидатором при загрузке уровня: конфликт = грани двух сплошных объектов лежат в одной плоскости (допуск 1 мм), **смотрят в одну сторону** и перекрываются по площади. Стык «встык» и стена-на-полу (грани навстречу) ошибкой не считаются — они всегда перекрыты ближней геометрией и не мерцают (отсечения задних граней в рендере нет, но оно и не нужно). Проверяются кубы окружения, двери, обрушаемые полы, переключатели и опасные зоны. Включается флагом `validate_geometry: true` в RON уровня; `cargo run -- --validate-level <имя>` проверяет всегда.
**Почему:** «Литейная» собрана с 596 такими конфликтами, «Утилизация» — с 15; это и было «прыгающие текстуры», на которые жаловался владелец. Правило «в одну сторону» выводит стыковку встык из-под подозрения — она правильный способ сборки.
**Отвергли:** полный запрет любых пересечений коробок — декор обязан утапливаться в стены; z-буфер без отсечения — бессмысленно, ближняя геометрия уже закрывает встречные грани. Существующие уровни не чиним и не валидируем — владелец распорядился не трогать их; новый уровень строится по правилам с флагом.

## 2026-10-29 — Игрок не сталкивается со случайностью в игровом процессе
**Решение:** игровой процесс детерминирован: поведение врагов, волн, механизмов и оружия предсказуемо, одинаковые действия игрока дают одинаковый результат. Псевдослучайный «шум» косметики (разлёт искр, крови, деталей) — детерминированные функции от счётчиков событий (hash, LCG), а не генератор случайных чисел. Случайность **вне** игрового процесса разрешена: генерация ассетов, звуков, dev-инструментов. Пакет `rand` не запрещён — добавляется по общим правилам зависимостей; сейчас удалён, потому что нигде не использовался.
**Почему:** игра про скилл: игрок должен понимать, что произойдёт, и учиться на повторениях. Предсказуемость нужна в геймплее, а не в инструментах разработки.
**Пересмотреть:** появится осознанное исключение в геймплее (например, лёгкая вариация косметики) — записать сюда отдельным решением.

## 2026-10-29 — Широкая фаза столкновений: рамки коробок вместо полного перебора
**Решение:** у каждой коробки уровня при сборке мира считается габаритная рамка (AABB), и каждый запрос (движение капсулы, касания, пересечение) сначала отбрасывает коробки, чья рамка не пересекается с областью запроса; узкая проверка parry3d запускается только для оставшихся. Луч выстрела отбрасывает далёкие коробки отдельным тестом луча по рамке.
**Почему:** на «Литейной» (516 коробок, 18 Болванок) полный перебор давал 10,6 мс на шаг логики — при 120 шагах в секунду и до 8 шагах за кадр это 10 кадров в секунду. После префильтра — 0,32 мс на шаг, в игре ~300 кадров в секунду. «Утилизация» с 41 коробкой не страдала, поэтому проблему не было видно до большого уровня.
**Отвергли:** пространственный хеш или BVH — на 516 коробках выигрыш уже не нужен, а поддерживать структуру при пересборке мира (двери, обрушаемые полы) дороже; вернуться, если коробок станет тысячи.

## 2026-10-29 — Сценарий уровня — триггеры и действия в RON, а не скриптовый язык
**Решение:** события уровня описываются списком триггеров, у каждого — зона, необязательный ключ и список действий (`Open`, `Close`, `Break`, `DisableHazard`, `Spawn`, `Say`). Имена объектов в действиях проверяются при загрузке и дают понятную ошибку.
**Почему:** уровень — это данные, а правка числа или порядка событий не требует компиляции; список действий закрыт и читается агентом без интерпретатора. Новый вид действия добавляется, только когда он реально нужен уровню.
**Отвергли:** встроенный скриптовый язык — второй рантайм, граница с Rust и собственные ошибки; вызовы Rust-функций из RON — хрупко и не читается человеком.

## 2026-10-29 — Контрольные точки: что сохраняется, что сбрасывается
**Решение:** точка запоминает центр нижней грани своей зоны, yaw игрока и свой номер в списке RON; работает только вперёд по списку. Смерть после точки — появление на ней с полным здоровьем и стаминой, активная арена возвращается в ожидание; открытые двери, сломанные полы, ключи, выключенные зоны, сработавшие триггеры и убитые Болванки сохраняются. `R` — всегда полный рестарт.
**Почему:** длинный уровень нельзя начинать заново после каждой смерти, но прогресс по сценарию не должен откатываться: игрок уже открыл ворота и сломал мостки. Арену сбрасываем, потому что её волны и станок — состояние боя, а не прогресс.
**Отвергли:** сохранять активную арену — после возрождения в её середине бой продолжается без игрока рядом, и волна может быть уже частично убита; хранить пройденные триггеры по имени — номер в списке надёжнее и переживает правку RON.

## 2026-10-29 — Механизмы уровня: префиксы имён и правила срабатывания
**Решение:** интерактивные объекты уровня задаются префиксом имени куба (`hazard_`, `pad_`, `belt_`, `crusher_`, `tube_`), числа — в RON уровня по имени объекта. Опасная зона наносит урон, когда **центр капсулы** внутри куба; плита, пресс и пневмопочта срабатывают, когда тело (от ступней до макушки) пересекает зону; лента — когда ступни стоят на её верхней грани. Плита подбрасывает, только если игрок не летит вверх.
**Почему:** префикс избавляет от списка объектов в RON и позволяет свободно копировать куб в Blender; центр капсулы для расплава — чтобы смерть наступала, когда игрок действительно в него погрузился, а не стоя на краю; проверка по телу нужна зонам у пола (плита в шахте — куб в 1 м на дне); без условия «не летит вверх» плита подбрасывала бы каждый шаг, пока тело внутри куба, и игрок улетал бы выше расчётного.
**Отвергли:** урон расплава по пересечению тела — умирать на краю нечестно; отдельные префиксы для «зоны» и «объёма» плиты — лишний вид объекта.

## 2026-10-29 — Стиль картинки: аркадный, не реалистичный
**Решение:** основной режим — `arcade`: светлая подсветка, пиксельные панели из шейдера, яркость граней по направлению, насыщенность, без тонмаппинга. Реалистичный свет (тени, отражённый свет) остаётся как настройки, но не задаёт вид игры.
**Почему:** человек хочет картинку, близкую к ULTRAKILL; на его скриншотах вид делают текстуры и цвет, а не физически правильный свет.

## 2026-10-29 — Освещение: тени из кубических карт, режимы и панель F3
**Решение:** тени от ламп уровня — кубические карты теней (до 24 ламп), перестраиваются только при смене уровня или настроек теней. Свет считается в линейном пространстве с тонмаппингом ACES. Внешний вид задаётся стилем освещения с режимами в `lighting.ron` и подбирается в панели F3.
**Почему:** у владельца проекта претензии к прежнему свету — проходит сквозь стены и некрасивый; он хочет сравнивать варианты сам. Лампы и стены статичны, поэтому кеширование карт делает тени почти бесплатными.
**Отвергли:** «запекание» света в текстуры (как в Quake) — красивее и дешевле в игре, но требует текстур и отдельного этапа подготовки уровня; вернуться, если тени в реальном времени не устроят. Готовый рендер-движок — противоречит решению делать свой.

## 2026-10-29 — Документы для человека в docs/
**Решение:** сложные системы (физика, свет, уровни и т.п.) описываются в `docs/` человеческим языком: обзор + раздел «Под капотом» с порядком действий, формулами и числами. Агент, меняющий систему, обновляет документ в той же задаче.
**Почему:** владелец проекта не читает код, но должен понимать устройство игры технически.

## 2026-10-29 — Отражённый свет запекаем сами на CPU
**Решение:** свой бейкер лайтмапов в `render/lightmap.rs`: уровень — только боксы, поэтому лучи пересекаются с OBB напрямую, без BVH и сторонних библиотек. Запекается только отражённый свет (1–4 отскока); прямой свет ламп остаётся в реальном времени с картами теней. Запекание при загрузке уровня, ~1,5 с в release.
**Почему:** даёт главное, чего не хватало, — свет в тенях и цветные отсветы — ценой одного файла без зависимостей. Прямой свет в реальном времени уже хорош и освещает врагов.
**Отвергли:** запекание в Blender (Cycles) — нужна UV-развёртка и ручной процесс на каждый уровень; GI в реальном времени (пробы, SDF) — много кода ради неподвижных ламп.
**Пересмотреть:** если запекание станет дольше нескольких секунд — кэшировать лайтмап в файл рядом с уровнем.

## 2026-10-29 — Режим скриншотов для проверки картинки агентами
**Решение:** `--screenshots [папка]` снимает все режимы освещения × кадры из `tools/screenshots.ron` и выходит.
**Почему:** агент сам видит результат правок рендера и находит ошибки без человека.

## 2026-10-28 — Ретро-эффекты лёгкие, а не полная имитация PS1
**Решение:** по умолчанию внутреннее разрешение — высота 480, глубина цвета — 7 бит на канал с дизерингом, дрожание вершин включено (при 480 оно мягкое). Все эффекты настраиваются в `settings_default.ron`.
**Почему:** владелец проекта попробовал 270 и 5–6 бит — слишком «прям PS1»; хочется точнее. Ретро-характер должны давать прежде всего модели и текстуры без фильтрации, как в ULTRAKILL.
**Отвергли:** 270 пикселей и 5 бит как в настоящем PS1 — остаются доступны в настройках.

## 2026-10-28 — Уровни в Blender собираются из кубов
**Решение:** геометрия уровня — только кубы (браши, как в Quake); загрузчик превращает каждый в бокс. Расстановка — по именам объектов (`player_start`, `enemy`, `target`, `arena_…`), правила арен и числа — в RON-файле уровня, ссылающемся на имена.
**Почему:** коллизии и рендер работают без изменений и остаются надёжными (бокс против капсулы). Числа удобнее держать в тексте, чем в свойствах объектов Blender.
**Отвергли:** произвольные меши с коллизией по треугольникам — больше кода и хрупкие нормали; свойства объектов glTF (extras) — понадобился бы ещё один пакет для разбора JSON.

## 2026-10-28 — Коллизия игрока — капсула с уточнением поверхности лучом
**Решение:** игрок — капсула 2,5×0,5 м. Каждое касание при движении дополнительно проверяется коротким лучом вниз в точке касания: «стоять можно» решается по нормали поверхности под лучом, а не по нормали касания капсулы.
**Почему:** владелец проекта выбрал капсулу на будущее (плавно обходит углы, одинаковая ширина во все стороны). У капсулы на рёбрах ступенек нормаль касания косая, и без луча ступенька неотличима от крутого склона.
**Известная ошибка parry3d 0.31:** когда капсула касается бокса ровно на нулевом расстоянии, `query::contact` возвращает ложное проникновение на метры с перевёрнутой нормалью. Обход: игрок всегда держит зазор `SKIN` (1 см) и появляется на уровне на `SKIN` выше точки старта; выталкивание игнорирует проникновения глубже радиуса. Регрессионный тест — `player_exactly_touching_floor_is_not_pushed_through_it`.
**Отвергли:** вертикальный бокс как в Quake — проще и надёжнее, но цепляется углами и шире по диагонали; был в коде как промежуточный вариант.

## 2026-10-28 — Раскладка клавиш через serde-фичу winit
**Решение:** у `winit` включена фича `serde`, клавиши в `settings_default.ron` записываются именами `KeyCode` (`KeyW`, `Space`, `ShiftLeft`).
**Почему:** раскладка должна лежать в данных; ручной разбор названий клавиш — лишний код.

## 2026-10-28 — Движение по схеме ULTRAKILL
**Решение:** база движения повторяет схему ULTRAKILL: бег 16,5 м/с, рывок 49,5 м/с, скольжение 24 м/с, 3 прыжка от стен, слэм 100 м/с, стамина 3 деления. Подробно в features/02-movement.md.
**Почему:** механики не охраняются, а эта схема проверена на миллионах игроков. Свои отличия добавим после плейтеста базы.

## 2026-10-28 — Blender 5.2.3 и бюджеты PS1
**Решение:** Blender закреплён на 5.2.3; рендер 480×270, текстуры 32–128 px, враги до 800 треугольников. Подробно в assets.md.
**Почему:** у владельца проекта установлен 5.2.3; бюджеты дают узнаваемый вид PS1.

## 2026-10-28 — Название 1681, английский первым
**Решение:** публичное название — «1681»; `ultrafun` остаётся именем репозитория и крейта (имя крейта не может начинаться с цифры). Язык — сначала английский, потом русский; весь текст для игрока с первого дня в `assets/text/<язык>.ron`.
**Почему:** перевод добавляется новым файлом без правок кода.

## 2026-10-28 — Workspace из двух крейтов: game и ultrafun
**Решение:** логика игры — отдельный крейт `game` без тяжёлых зависимостей; приложение `ultrafun` зависит от него. Контент — только данные в `assets/`.
**Почему:** правка логики не пересобирает рендер, тесты логики собираются меньше чем за секунду (замер: 0,86 с); граница архитектуры проверяется компилятором; новый уровень не требует компиляции.
**Отвергли:** один крейт — проще, но любая правка пересобирает всё приложение, а запрет на wgpu в логике держится только на дисциплине.

## 2026-10-28 — rust-lld на Windows
**Решение:** линковщик `rust-lld` в `.cargo/config.toml`.
**Почему:** замер на проекте с wgpu, egui, kira: пересборка 3,3–5 с со стандартным линковщиком против 1,8–2,1 с с rust-lld.

## 2026-10-28 — Лицензии: GPL-3.0 для кода, CC BY-SA 4.0 для контента
**Решение:** код под GPL-3.0-or-later, ассеты под CC BY-SA 4.0.
**Почему:** владелец проекта не хочет, чтобы игру можно было взять и закрыть; копилефт гарантирует, что форки останутся открытыми. CC BY-SA 4.0 совместима с GPL-3.0 в одну сторону.
**Отвергли:** MIT/Apache-2.0 и CC BY — разрешают закрытые форки.

## 2026-10-28 — Уровни в Blender, экспорт в glTF
**Решение:** уровни строятся в Blender, игровые объекты задаются именами объектов сцены, экспорт в `.glb`.
**Почему:** не нужно писать редактор и загрузчик второго формата; модели и уровни в одном формате.
**Отвергли:** TrenchBroom — быстрее строить арены, но нужен свой загрузчик карт. Вернуться, если строить арены в Blender станет больно.

## 2026-10-28 — Ассеты: только совместимые свободные лицензии
**Решение:** CC0, CC BY, CC BY-SA и свои работы; учёт в `assets/CREDITS.md`. Простые модели генерируются скриптами Blender в `tools/blender/`.
**Почему:** репозиторий открытый, мы распространяем сами файлы; «royalty-free» лицензии это запрещают. Скрипты делают модели воспроизводимыми и понятными агентам.

## 2026-10-28 — Логика игры отделена от всего остального
**Решение:** `game/` не зависит от окна, GPU, звука и устройств ввода; общается через действия на входе и `Vec<GameEvent>` на выходе. Подробно в architecture.md.
**Почему:** логику можно тестировать без окна, а правки рендера не ломают геймплей.

## 2026-10-28 — Платформы: Windows, Linux, SteamOS
**Решение:** Windows и нативный Linux; Steam Machine и Steam Deck через ту же Linux-сборку. macOS не поддерживаем.
**Почему:** так решил владелец проекта; SteamOS — это Linux, отдельной сборки не нужно.

## 2026-10-28 — Геймпад позже, ввод через действия сразу
**Решение:** `gilrs` пока не подключаем. Ввод с первого дня переводится в действия, игра не видит клавиш.
**Почему:** неиспользуемая зависимость противоречит принципам. Безболезненное добавление геймпада обеспечивает слой действий, а не ранее подключённый пакет.
**Срок:** до выпуска на Steam Machine / Steam Deck.

## 2026-10-28 — Настройки и сохранения в RON в системных папках
**Решение:** `directories` для путей, `ron` для формата, запись через временный файл.
**Почему:** RON уже используется для данных; системные папки — стандарт для обеих ОС.

## 2026-10-28 — Профилировщик Tracy
**Решение:** `tracy-client` под cargo-фичей `profile`.
**Почему:** самый мощный профилировщик для игр, не влияет на обычную сборку.
**Отвергли:** `puffin` — его интеграция с egui отстаёт от нашей версии egui.

## 2026-10-28 — Физика в два уровня
**Решение:** движение и бой — свой код с запросами к `parry3d` и фиксированным шагом 120 Гц. `rapier3d` — только для косметических эффектов в отдельном мире, не влияющем на геймплей.
**Почему:** продвинутые трюки движения — намеренно «нефизичные» правила, их проще писать напрямую, чем бороться с симуляцией. Эффекты разрушения при этом выглядят живо.
**Отвергли:** игрок как физическое тело и готовый контроллер персонажа из `rapier3d`.

## 2026-10-28 — Вдохновлено ULTRAKILL, но не клон
**Решение:** open source игра в духе ULTRAKILL со своим миром, персонажами и контентом.
**Почему:** механики и жанр брать можно, ассеты, имена и лор — нельзя ни юридически, ни по замыслу. Подробно в design/vision.md.

## 2026-10-28 — Rust без движка
**Решение:** Rust и свой минимальный движок на `winit` + `wgpu`; пакеты и версии в stack.md.
**Почему:** компилятор Rust ловит ошибки, которые агенты сами исправляют по сообщениям; `cargo` проще CMake. Графика в стиле PS1 достаточно проста, чтобы писать рендер самим.
**Отвергли:** C++ с raylib — быстрее старт, но ошибки памяти и сборка тяжело даются агентам. Bevy — по сути движок с нестабильным API.

## 2026-10-28 — Без скриптового языка
**Решение:** вся логика на Rust, настраиваемые числа в RON-файлах с перезагрузкой на лету.
**Почему:** логику и так пишут агенты; второй язык добавляет слой связки и ошибки на границе.
**Пересмотреть:** если время компиляции станет реальной проблемой.

## 2026-10-28 — Без ECS
**Решение:** сущности хранятся в обычных `Vec` структур.
**Почему:** для арены с десятками врагов ECS — лишняя сложность.

## 2026-10-28 — Код без комментариев
**Решение:** в коде нет комментариев, смысл передаётся именами, структурой и тестами.
**Почему:** проект пишут LLM-агенты; комментарии устаревают незаметно и вводят агентов в заблуждение.

## 2026-10-28 — Минимальные решения
**Решение:** делаем самое простое работающее решение, без абстракций на будущее.
**Почему:** простой код агенты понимают и меняют быстрее и с меньшим числом ошибок.
